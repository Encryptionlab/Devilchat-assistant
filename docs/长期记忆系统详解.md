## 一、三层记忆体系

```
时间尺度      层级              载体                    主要字段

短期（秒~分） Message          内存（不持久化）          surface_intent_scores
                                                       need_scores
                                                       emotion / intensity
                                                       每条消息处理完即释放

中期（时~天） Conversation     conversations.json       topic / start_time / end_time
                                                       summary / outcome / key_points
                                                       生命周期：active → closed

长期（周~月） Relationship     relationship_state.json  stage / trust_level
                                                       recurring_topics
                                                       unresolved_topics
                                                       conflict_level
                                                       持续累积，永不关闭
```

**核心原则**：

```
Message（分析她这句话在说什么）
    ↓
Conversation（记录这一段对话发生了什么）
    ↓  关闭时
Relationship Memory（记住关于这段关系的长期事实）
    ↓  启动时
Context Builder（把记忆注入 LLM 上下文）
```

## 二、储存层

### 2.1 relationship_state.json

**定位**：关系的长期画像。跨会话持久化，持续累积。

**存储路径**：`项目根目录/relationship_state.json`

**首次创建**：由 `bootstrap.py` 在首次运行时自动生成。

**完整 Schema**：

| 字段 | 类型 | 说明 | 维护方式 | 值域 |
|---|---|---|---|---|
| `当前关系阶段` | string | 关系发展阶段 | 手动（stage 永久人工确认） | stranger / acquaintance / friend / ambiguous / dating / stable |
| `关系热度` | string | 当前互动热度 | 手动 | hot / warm / neutral / cold / freezing |
| `对方依恋风格` | string | 心理学依恋类型 | 手动（null=未知） | secure / anxious / avoidant / fearful / null |
| `信任程度_0到100` | int | 她对你的信任度 | 手动 | 0-100 |
| `亲密程度_0到100` | int | 双方关系亲密度 | 手动 | 0-100 |
| `冲突状态` | string | 是否处于矛盾期 | 手动 | none / mild / active / severe |
| `近期关键事件` | list | 最近发生的重要事件 | 手动（最多 5 条） | 自由文本 |
| `conflict_level` | int | 冲突等级，自动维护 | MemoryUpdater 自动 | 0-5 |
| `recurring_topics` | list | 反复出现的话题 | MemoryUpdater 自动 | work / exam / family / relationship / dating / conflict |
| `unresolved_topics` | list | 未解决的问题 | MemoryUpdater 自动 | 自由文本 |
| `future_events` | list | 即将发生的事件 | 手动 | 自由文本 |
| `preferences` | list | 她的偏好和习惯 | 手动 | 自由文本 |
| `personality_traits` | list | 性格特征 | 手动 | 自由文本 |

**示例**：

```json
{
  "说明": "此文件手动维护。部分字段由 MemoryUpdater 自动更新。",
  "relationship_state": {
    "当前关系阶段": "dating 恋爱",
    "关系热度": "warm 温暖",
    "对方依恋风格": "anxious 焦虑型",
    "信任程度_0到100": 70,
    "亲密程度_0到100": 65,
    "冲突状态": "none 无冲突",
    "近期关键事件": ["下周六约会", "她最近工作压力大"],
    "conflict_level": 0,
    "recurring_topics": ["work"],
    "unresolved_topics": ["异地问题"],
    "future_events": [],
    "preferences": ["喜欢看悬疑片", "不吃辣"],
    "personality_traits": []
  },
  "更新日志": [
    {"日期": "2026-07-25", "修改字段": "conflict_level", "旧值": 1, "新值": 0, "原因": "冲突已修复"}
  ]
}
```

### 2.2 conversations.json

**定位**：对话的中期记录。记录已完成对话的摘要，供上下文和记忆更新使用。

**存储路径**：`项目根目录/conversations.json`

**由 `ConversationManager` 自动管理**（每次 `process_message()` 调用后自动保存）。

**Schema**：

```json
{
  "active": {
    "id": "conv_a1b2c3d4",
    "topic": "relationship",
    "status": "active",
    "start_time": "2026-07-25T14:00:00",
    "last_message_time": "2026-07-25T14:05:00",
    "current_goal": "AMPLIFY_POSITIVE",
    "summary": null,
    "outcome": null,
    "message_ids": ["msg_001", "msg_002"],
    "key_points": []
  },
  "closed": [
    {
      "id": "conv_e1677026",
      "topic": "work",
      "status": "closed",
      "start_time": "2026-07-25T10:00:00",
      "end_time": "2026-07-25T10:25:00",
      "last_message_time": "2026-07-25T10:25:00",
      "current_goal": "REDUCE_NEGATIVE",
      "summary": "她抱怨工作压力大，倾诉了30分钟。情绪从愤怒转为平静。",
      "outcome": "resolved",
      "message_ids": ["msg_010", "msg_011", "msg_012", "msg_013"],
      "key_points": ["她提到想换工作", "老板最近频繁施压"]
    }
  ]
}
```

**Conversation 字段说明**：

| 字段 | 类型 | 说明 | 何时填充 |
|---|---|---|---|
| `id` | string | 唯一标识 | 创建时 |
| `topic` | string | 话题标签 | 创建时（关键词检测） |
| `status` | string | active / closed | 创建/关闭时 |
| `start_time` | string | ISO8601 开始时间 | 创建时 |
| `end_time` | string | ISO8601 结束时间 | 关闭时 |
| `last_message_time` | string | 最后一条消息时间 | 每条消息更新 |
| `current_goal` | string | 当前对话目标 | 每条消息更新 |
| `summary` | string | LLM 生成的摘要 | **关闭时**（summarizer.py） |
| `outcome` | string | resolved / unresolved / neutral | **关闭时**（summarizer.py） |
| `key_points` | list | 关键信息点 | **关闭时**（summarizer.py） |
| `message_ids` | list | 消息 ID 列表 | 每条消息追加 |

**生命周期自动管理**：
- 最多保留 **50 个**已关闭 Conversation
- 超出自动丢弃最早的
- active Conversation 跨进程恢复

### 2.3 消息内容

**消息本身不持久化到磁盘**。消息文本仅在内存中保留，用于：
- 当前 Conversation 的上下文构建（最近 6 条注入 LLM prompt）
- Conversation 关闭时的摘要生成（完整对话传给 summarizer）

关闭后，消息文本被丢弃，只保留 Conversation 的 `summary` + `key_points`。

## 三、更新层

### 3.1 触发时机

```
Conversation 关闭
    │
    ├─ 时间间隔 > 8h
    ├─ 跨天（非深夜）
    ├─ 话题切换 + 间隔 > 30min
    ├─ 结束信号（晚安/拜拜/我去洗澡）+ 下条确认
    └─ 超时兜底（按 topic 差异化：daily 6h → conflict 72h）

    ↓

_on_conversation_closed()   ← run.py 交互循环中的关闭钩子
    │
    ├─ Step 1: summarizer.py → LLM 生成 summary + outcome + key_points
    ├─ Step 2: MemoryUpdater.update() → 规则驱动长期记忆更新
    ├─ Step 3: MemoryUpdater.apply_recurring_topics() → 话题重复检测
    └─ Step 4: 写回 relationship_state.json + conversations.json
```

### 3.2 MemoryUpdater 规则详解

**规则 1：recurring_topics（话题重复检测）**

```
触发：同一 topic 在最近 10 个已关闭 Conversation 中出现 ≥ 3 次
动作：将该 topic 写入 relationship_state.recurring_topics
示例：最近 10 次对话中 "work" 出现了 4 次 → recurring_topics: ["work"]
```

实现路径：`MemoryUpdater.apply_recurring_topics(topic_counts)`，需要外部提供 `{topic: count}` 计数。当前由交互循环中的 `conv_mgr.count_topic_in_recent(topic, n=10)` 提供。

**规则 2：unresolved_topics（未解决问题追踪）**

```
触发：Conversation outcome = "unresolved" 且 key_points 非空
动作：将 key_points 中的信息点追加到 relationship_state.unresolved_topics
示例：outcome=unresolved, key_points=["她想要更多陪伴"]
      → unresolved_topics: ["她想要更多陪伴"]
```

去重：同一 key_point 不会重复写入。

**规则 3：conflict_level +1（冲突升级）**

```
触发：topic = "conflict" 且 outcome = "unresolved"
动作：conflict_level += 1（上限 5）
示例：吵架了没和好 → conflict_level 从 1 升到 2
```

**规则 4：conflict_level -1（冲突修复）+ 清理 unresolved**

```
触发：topic = "conflict" 且 outcome = "repaired"
动作：
  1. conflict_level -= 1（下限 0）
  2. 从 unresolved_topics 中移除 key_points 中匹配的条目
示例：上次吵架的问题这次和解了 → conflict_level 从 2 降到 1，清理相关 unresolved
```

### 3.3 衰减机制（apply_decay）

**状态：已实现代码，尚未接入交互循环**（详见第六节）。

```
触发：定期检查（建议每次启动时调用一次）
逻辑：
  - 某 topic 超过 30 天未在最近 Conversation 中出现 → 降权标记（MVP 仅日志）
  - 某 topic 超过 60 天未出现 → 从 recurring_topics 中移除
输入：{topic: days_since_last_seen}  dict
```

### 3.4 引导式初始化（首次创建）

```
首次运行（relationship_state.json 不存在）
    │
    ├─ bootstrap.py 打印引导语
    │     "说说你们现在的关系吧..."
    │
    ├─ 用户输入一段自然语言描述
    │
    ├─ LLM 提取结构化字段
    │     → stage / temperature / trust_level / intimacy_level / ...
    │
    └─ 写入 relationship_state.json
          → 后续启动直接加载，不再触发引导
```

bootstrap 失败时（LLM 返回不可解析），回退到最小默认值：
- stage=acquaintance, temperature=neutral, trust=30, intimacy=20

### 3.5 stage 的人工确认机制

`stage` 字段不做自动更新（四个决策中已确定）。

在引导式初始化时，LLM 会从用户描述中**建议**一个 stage，但用户可以随时手动修改 `relationship_state.json` 中的值。系统不对 stage 做自动推断或覆盖。

未来可增加"检测到关系阶段可能已变化，建议更新"的提示——但只提示，不做自动修改。

## 四、上下文管理层

### 4.1 ContextBuilder 的三层精选

`context_builder.py` 负责在每次回复生成前，将长期记忆、当前对话、最近消息组装为 LLM 可消费的 prompt。

```
Layer 1: Relationship Memory      (~600 tokens)
    ↓   来自 relationship_state.json
    ├─ 关系阶段、热度、信任度、亲密程度
    ├─ recurring_topics（反复话题）
    ├─ unresolved_topics（未解问题）
    ├─ recent_events（近期事件）
    ├─ future_events（即将发生）
    └─ preferences / personality_traits

Layer 2: Current Conversation      (~200 tokens)
    ↓   来自 Conversation 对象（仅 active 状态）
    ├─ topic（当前话题）
    ├─ current_goal（当前目标）
    └─ summary（前情摘要，如果可获取）

Layer 3: Latest Messages           (~1200 tokens)
    ↓   来自内存中的消息列表
    └─ 最近 6 条对话
```

**注入位置**：构建结果通过 `format_for_llm()` 转为 markdown 文本块，注入到 `ReplyGenerator._build_user_prompt()` 的最顶部。

### 4.2 上下文在流水线中的流动

```
run.py 交互循环
    │
    ├─ 1. load_relationship_state()
    │      → rs dict（从 relationship_state.json）
    │
    ├─ 2. MessageUnderstanding(rs)
    │      → user_prompt 注入关系上下文（stage/trust/conflict），帮助消歧
    │
    ├─ 3. NeedRecognizer(rs).prioritize(ms)
    │      → 用 stage/trust/conflict 做乘法因子调整 need_scores
    │
    ├─ 4. GoalPlanner(rs).plan(ms, top_needs)
    │      → 用 conflict_status 做冲突优先覆盖
    │
    ├─ 5. ConversationManager.process_message()
    │      → 维护当前 Conversation 的生命周期
    │
    ├─ 6. ContextBuilder(rs_raw, conv, messages).format_for_llm()
    │      → 构建三层上下文文本块
    │
    ├─ 7. StrategySelector(rs).select()
    │      → 用 stage 做策略卡的阶段过滤
    │
    ├─ 8. ReplyGenerator(rs).generate(..., conversation_context=ctx)
    │      → 三层上下文文本块注入 user_prompt 顶部
    │
    └─ 9. ExpressionEnhancer(rs).enhance()
           → 用 stage 选择语气（STAGE_TONE 映射）
```

每一步中 `rs` 的具体使用方式：

| 步骤 | 使用 rs 的哪些字段 | 用途 |
|---|---|---|
| 消息理解 | stage, trust, intimacy, conflict, recent_events, attachment_style | user_prompt 注入关系语境 |
| 需求识别 | stage, trust, conflict_status, recent_events | 乘法因子调整 need_scores |
| 目标确定 | conflict_status | 冲突优先覆盖 |
| 上下文构建 | 全部字段 | Layer 1 长期记忆文本块 |
| 策略选择 | stage | 策略卡 relationship_stage 过滤 |
| 回复生成 | 全部字段 + 三层上下文 | 完整 prompt 构建 |
| 表达增强 | stage | 语气选择 |

### 4.3 rs 的加载策略

每次循环迭代开始时**重新加载** `relationship_state.json`：

```python
rs = load_relationship_state()
```

原因：`_on_conversation_closed()` 中 MemoryUpdater 会写回文件。如果不重新加载，下一轮循环拿到的 rs 是过期的（缺少刚写入的 recurring_topics 等更新）。

## 五、完整生命周期

### 5.1 首次启动

```
python run.py
    │
    ├─ relationship_state.json 不存在
    │     → bootstrap.py 引导对话
    │     → LLM 提取初始画像
    │     → 写入 relationship_state.json
    │
    └─ 进入交互循环
```

### 5.2 正常对话流程

```
她: 今天工作好累啊
    │
    ├─ 消息理解（LLM）：emotion=tired, need=EMOTIONAL_RELEASE+SUPPORT
    ├─ 需求识别（规则）：叠加阶段/事件/情绪因子
    ├─ 目标确定（规则）：REDUCE_NEGATIVE
    ├─ Conversation 引擎：topic=work, 创建新 conv（或继续已有的 work conv）
    ├─ 上下文构建：Layer1 长期记忆 + Layer2 当前 conv + Layer3 消息
    ├─ 策略选择（规则）：匹配 care_vs_attention
    ├─ 回复生成（LLM）：生成回复
    ├─ 表达增强（LLM）：口语化
    │
    └─ 回复: 工作确实累，先好好休息。最近压力这么大吗？
```

### 5.3 Conversation 关闭 → 记忆写入

```
她: 晚安
    │
    ├─ 检测到结束信号 → _pending_close = True → 本轮继续回复
    │
她: （第二天早上）早啊
    │
    ├─ 确认关闭（pending_close 上轮为 True）
    │
    ├─ _on_conversation_closed()
    │     ├─ summarizer.py → LLM 摘要
    │     │   summary: "昨晚她抱怨工作压力大，情绪从低落转为平静。"
    │     │   outcome: "neutral"
    │     │   key_points: ["她最近工作压力大", "想换工作"]
    │     │
    │     ├─ MemoryUpdater.update(closed_conv)
    │     │   → outcome=neutral → 不触发规则 2/3/4
    │     │
    │     ├─ MemoryUpdater.apply_recurring_topics({"work": 3})
    │     │   → work 出现 3 次 → recurring_topics: ["work"]
    │     │
    │     └─ 写回 relationship_state.json
    │
    └─ 新建 Conversation: topic=daily
```

### 5.4 后续启动

```
python run.py（第二天）
    │
    ├─ relationship_state.json 存在
    │     → load_relationship_state()
    │     → recurring_topics: ["work"], conflict_level: 0
    │
    ├─ conversations.json 存在
    │     → 如果上次有未关闭的 active conv → 恢复
    │     → 如果上次已关闭 → active=None，等第一条消息
    │
    └─ 进入交互循环（所有记忆已就位）
```

### 5.5 长期运行效果

```
一周后（多次对话积累）

relationship_state.json:
  ├─ recurring_topics: ["work", "relationship"]   ← 检测到反复话题
  ├─ unresolved_topics: ["异地问题"]               ← 某次对话未解决
  ├─ conflict_level: 1                            ← 发生过一次吵架
  └─ recent_events: ["下周末约会"]                  ← 手动或自动更新

ContextBuilder 注入到 LLM 时：
  Layer 1 包含：
    "反复出现的话题: work, relationship"
    "未解决的问题: 异地问题"
    → LLM 在生成回复时会自然地考虑这些背景
    → 例如她抱怨工作，LLM 知道这是反复话题，会更认真对待而非简单安慰
```

## 六、当前缺口

### 6.1 apply_decay() 未接入

- **代码状态**：`memory_updater.py` 中已实现 `apply_decay()`
- **问题**：recurring_topics 只增不减
- **影响**：长期（数月）后可能残留过期条目
- **优先级**：低
- **建议**：每次 `run.py` 启动时调用一次，基于 conversations.json 中各 topic 最近出现日期计算 ages dict

### 6.2 trust_level / intimacy_level 渐进演化未实现

- **当前状态**：纯手动
- **理想状态**：事件驱动微调（每次正常对话结束 +1，冲突 unresolved -2，自我披露 +1）
- **优先级**：中
- **原因暂缓**：需要消息理解层输出 self_disclosure 标志，改动面较大

### 6.3 recent_events 自动更新未实现

- **当前状态**：纯手动
- **理想状态**：从 Conversation summary 的 key_points 中提取
- **优先级**：中
- **依赖**：需要 MemoryUpdater 或新模块支持

### 6.4 消息历史跨进程恢复未实现

- **当前状态**：消息文本不持久化。进程退出后，未关闭 Conversation 的消息历史丢失
- **影响**：如果程序在 Conversation 中途退出，重启后该 conv 被恢复但 message_ids 对应的消息内容不可恢复。Conversation 关闭时 summary 将缺少消息内容
- **优先级**：中
- **临时代偿**：有 active conv 时退出程序会丢失消息文本，summary 生成受影响。建议每次退出前确保当前 conv 已自然结束，或接受丢消息的风险

### 6.5 异步摘要生成

- **当前状态**：Conversation 关闭时同步调用 LLM 生成摘要（阻塞 2-3 秒）
- **影响**：用户在关闭发生时等待时间略长
- **优先级**：低
- **当前评估**：终端聊天场景可接受

## 八、文件一览

| 文件 | 职责 | 内存/持久 |
|---|---|---|
| `relationship_state.json` | 长期关系画像 | 持久 |
| `conversations.json` | 对话中期记录 | 持久 |
| `message_understanding.py` | 消息分析 + 关系状态加载 | 内存 |
| `bootstrap.py` | 首次运行引导初始化 | 持久写入 |
| `conversation.py` | Conversation 生命周期管理 | 持久读写 |
| `memory_updater.py` | 长期记忆规则更新 | 持久读写 |
| `summarizer.py` | LLM 对话摘要生成 | 写入 Conversation 对象 |
| `context_builder.py` | 三层上下文组装 | 内存 → LLM prompt |
| `run.py` | 交互循环 + 关闭钩子 | 编排层 |
