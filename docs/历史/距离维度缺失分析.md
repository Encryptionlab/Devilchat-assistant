# 距离维度缺失分析

版本: v2 MVP | 日期: 2026-07-25 | 状态: 待评估

---

## 一、问题陈述

当前系统的 `relationship_state.json` 只捕获了关系发展的**纵向深度**（stage: stranger → acquaintance → friend → ambiguous → dating → stable），完全缺失了**横向空间距离维度**。

同一恋爱阶段下，距离模式不同，回复策略应当不同。目前系统无法区分。

---

## 二、四种距离模式

| 模式 | 定义 | 见面频率 | 典型场景 |
|---|---|---|---|
| `same_city` | 同城 | 随时可约 | 同城恋爱、同校、同公司 |
| `short_separation` | 短期分离 | ≤30 天内恢复 | 出差、旅行、探亲、假期回家 |
| `long_distance` | 异地恋 | 偶尔见面（月/季度） | 不同城市、跨国 |
| `online_only` | 纯网恋 | 从未见面 | 社交 App 匹配、游戏 CP |

---

## 三、对系统行为的具体影响

### 3.1 消息理解层 —— 同一句话在不同距离下含义不同

| 她说 | 同城恋爱 | 异地恋 |
|---|---|---|
| "我想你了" | 撒娇，今晚可约见面 | 真实思念+无力感，可能带有 sadness |
| "你在干嘛" | 闲聊/想你了 | 查岗/需要安全感（SECURITY） |
| "周末有空吗" | 日常邀约 | 重大事件（可能她来找你或你去找她） |
| "我好累" | 求安慰，想让关心 | 可能暗示撑不下去了（COMPANIONSHIP 需求更强烈） |
| "今天看到一个很好吃的店" | 想一起去 | 遗憾感，可能演变为抱怨异地 |
| "我去洗澡了" | 正常结束信号 | 可能只是不想聊了，未必真要结束 |

### 3.2 需求识别层 —— 距离因子缺失

以下场景在 `need_recognition.py` 中完全不被感知：

**异地恋应具有的持续调整：**

- SECURITY 需持续加成（距离本身就制造不安全感，这是恒定的背景因子）
- COMPANIONSHIP 需结构性惩罚（你无法物理陪伴，"我在"类回复显得空洞）
- INTIMACY 需更谨慎（文字是唯一载体，过度亲密表达容易显得廉价）

**纯网恋应具有的持续性调整：**

- INTIMACY 需软惩罚（未见面时过度推进亲密有风险）
- RESPECT 需加成（网恋更需尊重边界，不能施压）
- SECURITY 需加成（没见过面，不确定性天然更高）

**短期分离应具有的临时调整：**

- SUPPORT 临时加成（她独自面对事情时更需要实际帮助）
- ENTERTAINMENT 临时加成（分离期需要更多情绪价值）

### 3.3 策略选择层 —— 距离约束缺失

策略卡的 `apply_when` 和 `not_apply_when` 只有 `relationship_stage` 和 `conversation_stage` 两个维度，没有距离过滤。

| 策略卡 | 当前状态 | 距离维度缺失的问题 |
|---|---|---|
| `signal_escalation` | 暧昧期可用 | 异地时释放信号无物理反馈，需更保守 |
| `care_vs_attention` | 根据 need 切换 | 异地无法"关注"（观察不到），只能"关心"（主动问） |
| `eighty_twenty_rule` | 通用 | 异地时 8 分关注 2 分引导比例需调整 |
| `humorous_deflection` | 抱怨/攻击时可用 | 异地时用幽默转移可能被解读为不在乎 |
| `validate_emotion_express_need` | 需要犹豫/信号时可用 | 异地时需要更强力度的共情验证 |
| `escalating_conflict` | 冲突升级时可用 | 异地冲突无法当面和解，需特殊处理 |

### 3.4 表达增强层 —— 语气错配

```python
# expression_enhancer.py 当前 STAGE_TONE
"dating": "亲密、自然，可以适度表达喜欢"
```

同样的 `dating` 阶段，**同城**和**异地**的语气差异：

| 维度 | 同城 dating | 异地 dating |
|---|---|---|
| 温度 | 自然日常 | 需要更多文字温度（不能靠肢体语言） |
| 频率 | 随意的日常感 | 每条消息都承载更多重量 |
| 结束语 | "拜拜" | 需要更温暖的道别（晚安+安全感锚点） |
| 昵称 | 自然使用 | 适度使用（文字过热容易腻） |

### 3.5 Conversation 引擎层 —— 话题分类不受影响

`conversation.py` 的话题检测和边界判断不依赖关系状态，此处无影响。

## 五、设计要点

### 5.1 `stage` 与 `distance_mode` 正交

二者独立维护，组合产生实际行为差异：

```
(stage=dating, distance=long_distance) ≠ (stage=dating, distance=same_city)
```

### 5.2 距离会影响但不应决定底层决策

- `needs` 的核心逻辑（LLM 分析：她在表达什么需求）不应被距离改变
- 距离应该影响的是：need 因子调整、策略选择、表达方式
- 即：底层理解不变，上层执行调整

### 5.3 `short_separation` 需要恢复机制

短期分离结束后应该恢复为 `same_city`，这在当前手动维护的模式下依赖用户自行修改。后续若做 Memory Updater 自动化，可基于事件（"她回来了"）触发恢复。

---

## 六、不做的事项

- 不做距离 → `stage` 的反向调整（距离模式不应该自动修改关系阶段）
- 不做"见面倒计时"等时间敏感功能（属于 P3 之后的锦上添花）
- `online_only` → `same_city` 的过渡（奔现）暂不做专项处理（先靠用户手动改 stage）

---

## 七、总结

当前系统的关系模型是**一维的**（只有纵向阶段），而现实中恋爱关系的空间距离是一个无法忽略的**独立维度**。缺失这个维度导致同一回复策略在不同距离场景下效果差异巨大，从"合适"变成"空洞"甚至"冒犯"。

建议将此作为 v3 专项迭代，在所有模块中补齐距离感知能力。
