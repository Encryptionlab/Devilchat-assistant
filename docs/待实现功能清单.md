## 二、P1 — 重要功能缺口

### 2.1 批量消息理解第二步：数据源切换到 messages_log

**当前状态**：v2 第一步已完成（序列化输入），但数据源仍是 MessageBuffer。第二步需要切到 ConversationManager.messages_log，同时拆分 CM 职责（`log_message` + `process_boundary`）解决循环依赖。

**循环依赖问题**：
```
MessageUnderstanding → 需要 CM.messages_log
CM.process_boundary   → 需要 MU.topic
```

**方案**（已设计，见 `消息理解思考coze.md` 第 4 节）：
- CM 拆分为两个阶段：`log_message()`（轻量记录）→ `process_boundary()`（边界检测）
- pipeline 顺序调整为：log_message → MU → Need → Goal → process_boundary

**改动量**：~25 行（CM 拆分）+ ~5 行（pipeline 数据源切换）

### 2.2 Evaluator 完整数据闭环

**当前状态**：`pipeline_service.py` 的 `_run_evaluator()` 中 `her_messages_before` 和 `my_message` 为空占位符。当前只能基于她当前消息的情绪变化做评估，看不到"我发了什么 → 她回应了什么"的完整链条。

**目标**：从 ConversationManager.messages_log 中提取 "我上一条消息"和"她之前的消息"，填充 Evaluator 的 before/after 数据。

**不依赖 WCF**：mock 数据包含双方消息，messages_log 已有完整记录。直接从 messages_log 取即可。

**改动量**：~20 行（`_run_evaluator()` 从 messages_log 提取上下文）

### 2.3 策略效果数据驱动 StrategySelector

**当前状态**：`strategy_effectiveness` 在 relationship_state.json 中持续累积数据（使用次数、成功率），但 StrategySelector 完全不用这些数据。策略推荐仍基于纯规则（双维度过滤 + need 匹配），不考虑历史成功率。

**目标**：当某策略在特定情绪/需求组合下成功率显著低于平均值时，降低其推荐优先级。当某策略历史表现优秀时，提升其权重。

**触发条件**：每个策略至少 20 次使用记录后（当前仅共情策略有 2 次）。

**改动量**：~30 行（在 StrategySelector 中加一个加权环节）

### 2.5 unresolved_topics 自动清理

**当前状态**：`unresolved_topics` 只在 conflict+repaired 时由规则 4 清理。非冲突类未解决问题（如"她考试压力大"类 topic）永远不会被清理。

**风险**：每条 unresolved 条目是完整句子，10-20 条累积可达 500-1000 tokens，严重挤压 LLM prompt 预算。

**方案**（二选一）：

A. 硬上限：`unresolved_topics` 最多保留 10 条，超出时 FIFO 移除
B. 时间衰减：超过 60 天未在任何 Conversation 中提及的 unresolved 条目自动移除

**改动量**：~15 行

### 2.6 personality_traits / preferences / future_events 写入通路

**当前状态**：这三个字段在 relationship_state.json 中定义，bootstrap 时可能填充，但 Conversation 关闭后从不自动更新。

**目标**：Conversation 摘要中包含对对方性格/偏好/未来计划的观察时，通过规则写入对应字段。

**设计难点**：需要从摘要文本中识别出"可写入的性格描述"——纯规则很难做到。可能需要一次额外的 LLM 调用（从摘要提取结构化信息），或者保持手动维护。

**改动量**：不确定（取决于方案选择）

## 三、P2 — 增强型功能

### 3.1 WCF SDK 接入（独立模块）

**当前状态**：消息通过 `POST /api/observe` 手动模拟流入，`backend/services/wcf_client.py` 未编写。

**目标**：接入 WeChatFerry SDK，实现微信消息自动流入 MessageBuffer。

**说明**：WCF 为独立模块，不影响其他逻辑的开发调试。mock 数据（`data/mock_wcf_story_3000.jsonl`）可替代 WCF 进行所有后端逻辑测试。

**改动量**：~200 行（新文件）

### 3.2 风险检查模块

**当前状态**：流水线中第 9 步标记为预留但未实现。

**功能**：在回复生成后，检查建议回复是否包含风险信号（如：过度承诺、可能激化冲突的措辞、不符合当前关系阶段的越界言论），给出风险提示。

**改动量**：~50 行（新模块 + pipeline 增加一个步骤）

### 3.3 回复评分模块

**当前状态**：流水线中第 10 步标记为预留但未实现。

**功能**：对生成的建议回复进行质量评分（共情度、策略匹配度、语气合适度等），帮助用户判断建议是否可信。

**改动量**：~50 行（新模块 + pipeline 增加一个步骤）

### 3.4 仪表盘实时推送

**当前状态**：仪表盘通过 10 秒轮询获取数据。WCF 接入后可能有较高频次的消息流入，需要更实时的通知。

**方案**：SSE 或 WebSocket 推送新消息到达事件 → 前端实时更新待处理数量 + 紧急度指示。

**说明**：WCF 为独立模块，mock 数据可替代。不阻塞开发。

**改动量**：~40 行（新增 SSE endpoint + 前端 hook 调整）

### 3.5 多联系人支持

**当前状态**：系统假设只有一个联系人（全局单例 MessageBuffer + ConversationManager）。

**目标**：支持多个联系人（多个她），数据按 wxid 隔离。

**改动量**：较大（MessageBuffer、ConversationManager、StateService 均需改造，数据模型需加 contact_id 维度）

### 3.6 历史聊天记录全量导入

**当前状态**：系统只处理 WCF 实时流入的消息。

**目标**：支持从微信导出的历史聊天记录（txt/csv 格式）全量导入，初始化关系记忆。

**改动量**：~100 行（导入解析器 + pipeline 批量处理）

## 四、P3 — 远期方向

### 4.1 Goal Chain

**当前状态**：ConversationManager 的 MVP 设计明确不包含 Goal Chain（跨消息的目标序列）。每个消息独立规划 Goal，不追踪 Goal 之间的递进关系。

**远期目标**：追踪"上一个 Goal 是否达成了 → 下一个 Goal 应该是什么"的链式关系。

### 4.2 Emotion Trajectory（会话级）

**当前状态**：MessageUnderstanding 已支持 burst 级的情绪递进（trajectory_note）。但 Conversation 维度还没有情绪轨迹追踪——一个话题持续 2 小时，她的情绪如何变化。

**远期目标**：在 Conversation 内记录情绪变化序列（多条 burst 的 emotion 形成时间线），关闭时作为摘要输入。

### 4.3 Pending Memory 置信度系统

**当前状态**：MemoryUpdater 设计文档提到"Pending memory 字段预留，MVP 不实现完整置信度计算"。当前写入基于硬规则（出现 ≥3 次即写入），不评估"这条信息是否足够可信"。

**远期目标**：每条待写入的长期记忆带置信度评分，低于阈值的不写入，避免噪音记忆污染。

### 4.4 个人化策略权重自优化

**当前状态**：2.2 是基础版（基于全局成功率调权）。远期目标是个性化：她生气时"共情"策略对「你」用效果好、对「别人」用效果未必好——因为她是跟你吵架。策略权重需要考虑"她跟我互动"的独特性。
