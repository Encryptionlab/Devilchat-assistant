## 1. Affinity Agent — 情感感知虚拟伴侣框架

**GitHub**: `maniac8/galgame-emotion-agent`

### 项目简介

为关系模拟游戏和互动叙事构建的情感感知虚拟伴侣框架。维护具有长期记忆、动态关系演化和结构化日常生活的持久化角色。关系成长跨越"陌生人 → 熟人 → 长期羁绊"多个阶段，进展取决于信任、共享经历、冲突修复和玩家行为，而非简单的亲密度数值。

### 值得借鉴的点

**多维度关系建模。** 关系以 11 个独立维度建模：熟悉度、信任、舒适度、紧张度、修复债务等。角色可能"喜欢玩家但不完全信任"、"感觉亲近但仍保持边界"。我们的 relationship_state 只有 5-6 个标量字段，可以吸收这种多维度思路——特别是"紧张度"和"修复债务"两个维度，可以直接映射到冲突管理。

**类型化记忆架构。** 记忆按类型组织：用户事实、共享事件、承诺、边界、冲突、情感时刻、关系里程碑。每种类型的记忆在不同场景下被选择性检索。我们的 Conversation 摘要目前是扁平的文本摘要，可以借鉴类型化思路——对话关闭时不只生成一段 summary，而是按类型分类存储关键信息。

**故事事件导演。** 基于规则的系统，根据前置条件和关系状态决定何时触发游戏内事件（初次见面、失约冲突、道歉修复、告白）。我们的 conflict_level 追踪和 recurring_topic 检测已经构成类似的前置条件逻辑，缺的是一个"主动提醒"层——当检测到 conflict_level 上升 + unresolved_topics 积累，可以主动提醒用户处理。

**多模型路由。** 不单靠一个大模型：强 roleplay 模型做回复生成、低成本模型做记忆提取、快速分类器做安全检查、推理模型做一致性审核。我们当前所有 LLM 调用用同一个 DeepSeek 模型——未来可以用更小/更快的模型处理紧急度评分、边界检测等轻量任务。

## 2. ConvoLens — 对话智能分析平台

**GitHub**: `santanu949/Convolens`

### 项目简介

基于 RAG 的对话智能分析平台。分析 WhatsApp 数据集（191,592 条消息，11,001 段对话），支持自然语言查询（"这个用户是什么样的人？"）并返回带引用来源的结构化答案。完全本地运行，不依赖外部 API。

### 值得借鉴的点

**证据溯源。** 每个提取的人格特征都附带原文引用数组——"她经常抱怨工作"后面跟着 3 条真实的原消息。我们的 memory_updater 写入长期记忆时没有保留证据链，Conversation 摘要生成后关键信息就脱离了原文上下文。可以给每条 recurring_topic / unresolved_topic 附带来源消息引用，让用户能回溯判断"这个结论靠不靠谱"。

**混合检索融合。** 语义嵌入 + TF-IDF 关键词搜索的加权融合（0.6/0.4），避免纯语义搜索遗漏精确关键词。这个权重分配思路可借鉴到我们的对话信息检索——当前系统只能按时间/话题查对话，未来要支持"她上次提到考试是哪天"这类的自然语言查询，就需要这种混合检索。

**话题边界检测的滑动窗口。** 用连续 3 条消息的 embedding 余弦相似度检测话题切换——低于 0.35 即标记边界，短对话用 TF-IDF 关键词偏移作为回退。我们的 ConversationManager 边界检测基于关键词 + 时间间隔 + 结束信号的纯规则系统，可以对比这种 embedding 方案——对隐性话题切换（不包含关键词但语义变了）更敏感。

**离线/在线分离。** 全量数据在首次启动时完成解析 + embedding 生成，持久化到 SQLite。后续查询不再重复计算。我们目前每次启动都是冷启动，Conversation 历史只被加载不会被预计算——如果要做更复杂的跨会话分析，需要这种预处理层。

## 3. Threa — 对话聚类与知识备忘录去重

**GitHub**: `threahq/threa` PR #1131

### 项目简介

修复 DM 对话聚类和知识备忘录提取系统的两个级联失败：对话边界检测缺少时间感知导致多天消息被吸入同一个对话；备忘录去重在流级别产生重复。PR 包含 22 个评估用例，全部通过。

### 值得借鉴的点

**时间是证据，不是规则。** 硬编码">24h 的对话自动关闭"很简单但错误——存在合法的次日继续和显式话题复活。Threa 的做法：把时间渲染进 prompt（"26h ago"、"last active 2d ago"），让 LLM 自己权衡。我们的 ConversationManager 的 8 小时自动关闭和跨天逻辑也是硬编码——可以借鉴"软时间"思路，在边界决策时提供时间上下文而非断然切割。

**LLM 的流程式 prompt 比散文式 prompt 更精确。** 散文形式的会话模型描述在 6.5 小时间隔测试中只有 60-75% 通过率。重构为有序决策流程后提升到 100%。我们的系统 prompt（MessageUnderstanding、ReplyGenerator 等）目前都是散文式——在需要精确决策的场景（边界检测、策略选择），可以考虑改为流程式。

**上游错误的下游放大效应。** 对话吸收（多天消息合并为一个对话）触发了全量重分类 → 每次新消息都导致大规模重处理。一个边界错误级联造成资源浪费。我们的 observe_messages() 每次消息进来都跑整个批量 MU——如果边界检测出错导致话题混杂，后续分析也全受影响。

**流级别去重。** 不再信任 revision prompt（同一机制不能既犯错又自我纠正），改为 embedding 距离门控（cosine < 0.15）作为唯一去重权威。我们的 memory_updater 写入逻辑中，recurring_topics 基于出现次数，但没有做语义去重——"考试压力大"和"考研复习好累"可能是同一件事的不同说法，当前系统会当成两个独立话题。

## 4. AI-GF-python — 情感陪伴聊天机器人

**GitHub**: `rishabhxchoudhary/AI-GF-python`

### 项目简介

基于 Hugging Face Inference API 的情感陪伴聊天机器人。具有 15 种动态演化的人格特征、4 阶段关系进展、时间感知行为调整、主动发起话题的能力。多 burst 消息模拟自然打字节奏。所有数据本地 JSON 持久化。

### 值得借鉴的点

**人格特征的自然漂移。** 15 种人格特征（自信、脆弱、顽皮等）随时间自然漂移，防止"性格固化"。我们的 relationship_state 中 personality_traits 字段目前为空——如果未来自动写入，也应该有漂移机制（最近的 trait 权重更高，旧的逐渐衰减）。

**时间感知的行为调整。** 根据时段调整能量水平和沟通风格（早晨/深夜有不同的 persona）。我们的系统目前完全时间无关——紧急度评分虽然考虑了夜间阻尼因子，但回复策略不感知时间。深夜她发的"好累"和白天的"好累"可能需要不同的回应策略。

**主动对话管理。** Bot 主动发起话题、追问、处理对话沉默，而不是被动等待输入。这给了我们一个思路：干预轨道不仅是"用户打开仪表盘 → 分析"，系统也可以在检测到特定条件时主动建议"现在可能是联系她的好时机"（基于她的活跃时间模式 + 关系状态变化 + 未解决问题积累）。

**分层 prompt 模板。** 系统 prompt、planner prompt、动态上下文、人格影响、时间指引——多个 prompt 片段按需组装。我们的 prompt 构建（MessageUnderstanding、ReplyGenerator 等）已经是分层设计，但可以进一步模块化——把"当前关系阶段对策略的约束"作为独立模块插入各个 prompt，而非在每个 prompt 里重复写关系上下文。

## 总结：对本项目最有价值的 5 个启发

| 来源 | 启发 | 对应模块 |
|------|------|---------|
| Affinity Agent | 类型化记忆（按事件类型存储而非 flat summary） | MemoryUpdater |
| ConvoLens | 证据溯源（每项长期记忆附带消息引用） | MemoryUpdater |
| Threa PR #1131 | 流程式 prompt > 散文式 prompt（高精度决策场景） | ConversationManager、StrategySelector |
| Threa PR #1131 | 流级别语义去重（embedding 门控） | MemoryUpdater |
| AI-GF-python | 主动建议触发（检测到条件时提醒用户行动） | 仪表盘/通知 |
