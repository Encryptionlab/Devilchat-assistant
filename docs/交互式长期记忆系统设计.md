# 交互式长期记忆系统设计

Version: 1.0 | 2026-07-25 | 状态: 待开发

---

## 零、背景与目标

### 当前问题

1. `relationship_state.json` 必须手动创建，首次运行文件不存在则系统崩溃
2. MemoryUpdater（v2 已实现 207 行代码）从未接入流水线，自动记忆回路是断的
3. Conversation 关闭时不生成 summary 和 outcome，MemoryUpdater 的规则依赖这些字段
4. CLI 单次执行模式无法支持日常多轮对话

### 本次目标

```
首次启动 → 引导式初始化（LLM 推导关系画像）
    ↓
交互式循环（持续接收消息 → 输出回复）
    ↓
Conversation 关闭时 → 自动生成摘要 → MemoryUpdater 写长期记忆
    ↓
下次启动 → 记忆自动加载，关系画像持续累积
```

### 四项决策（已确定）

| 决策 | 结论 |
|---|---|
| 初始化策略 | B 路线：引导对话 → LLM 推导初始画像 |
| stage 自动化 | 人工确认，系统提示用户提供信息 |
| 运行模式 | 交互式循环，Conversation 关闭时触发记忆写入 |
| 纠错机制 | 暂缓，等问题真实出现再设计 |

### 步骤 1：文件不存在容错

**位置**：`message_understanding.py` 的 `load_relationship_state()`

**当前行为**：
```python
if not filepath.exists():
    raise FileNotFoundError(...)
```

**改为**：
```python
if not filepath.exists():
    return _default_state()
```

**默认值**（文件不存在时返回）：
```python
{
    "stage": "",
    "temperature": "",
    "attachment_style": None,
    "trust_level": 0,
    "intimacy_level": 0,
    "conflict_status": "none",
    "recent_events": [],
}
```

**影响**：消息理解 prompt 中关系上下文可能为空或全 0。LLM 在缺少关系上下文时仍能分析消息本身（情绪、意图），只是消歧能力弱一些。等初始化完成后恢复正常。

**验收**：删除 `relationship_state.json`，运行 `MessageUnderstanding()` 不崩溃。

### 步骤 2：引导式初始化（bootstrap.py）

**定位**：首次运行时，通过一段引导对话让用户描述关系状况，LLM 从中提取初始画像。

**流程**：

```
用户首次启动
  ↓
检测 relationship_state.json 不存在
  ↓
打印引导语
  ↓
用户自由输入（一段自然语言）
  ↓
LLM 解析 → 写入 relationship_state.json
  ↓
进入交互循环
```

**引导语**：

```
欢迎使用魔鬼聊天。

在开始之前，先简单说说你们现在的关系吧。
比如：
  - 认识多久了？怎么认识的？
  - 现在是什么关系阶段？（刚认识 / 朋友 / 暧昧 / 恋爱 / 稳定）
  - 最近有什么重要的事情发生吗？
  - 你觉得她信任你吗？你们亲密吗？

不用拘束，像跟朋友聊天一样描述就好。
```

**LLM 解析 prompt**（核心：从自然语言提取结构化字段）：

```
你是一个关系状态分析助手。用户会用自然语言描述一段恋爱关系。
请从描述中提取以下字段，仅输出 JSON。

字段说明：
- stage: 关系阶段，可选值 stranger / acquaintance / friend / ambiguous / dating / stable
- temperature: 关系热度，可选值 hot / warm / neutral / cold
- attachment_style: 对方依恋风格，可选值 secure / anxious / avoidant / fearful，不确定填 null
- trust_level: 信任程度 0-100
- intimacy_level: 亲密程度 0-100
- recent_events: 近期关键事件列表（最多 5 条）
- conflict_status: 冲突状态，可选值 none / mild / active
- notes: 其他值得注意的信息（一段话）

如果用户没有提到某个字段，给出合理推测并标注 confidence。

仅输出 JSON，不要包含其他文字。
```

**生成的 JSON 写入 `relationship_state.json`**，格式与现有文件一致（保持向后兼容）。

**验收**：删除 `relationship_state.json`，启动系统，输入一段描述，检查生成的文件是否包含正确的字段和合理的值。

### 步骤 3：Conversation 摘要器（summarizer.py）

**定位**：当 Conversation 关闭时，调用 LLM 生成摘要、判断结局、提取关键信息点。这是 MemoryUpdater 的数据来源。

**输入**：已关闭的 Conversation 对象（含所有消息）

**LLM prompt**：

```
你是一个对话分析助手。以下是一段已结束的对话。

请分析并仅输出 JSON：
{
  "summary": "2-3句话概括这段对话的内容和走向",
  "outcome": "resolved / unresolved / neutral",
  "key_points": ["关键信息点1", "关键信息点2", ...],
  "topic": "对话主题标签"
}

outcome 判断标准：
- resolved: 问题得到解决，情绪得到安抚，或达成了共识
- unresolved: 问题未解决，矛盾仍在，或情绪未平复
- neutral: 日常闲聊，无所谓解决不解决

key_points: 提取对话中值得记住的信息，例如"她提到想换工作"、"约定下周六见面"
```

**输出**：写入 Conversation 对象的 `summary`、`outcome`、`key_points` 字段，然后持久化到 `conversations.json`。

**注意**：summary 生成后，Conversation 才能在后续上下文中被引用（ContextBuilder Layer 2 会展示"前情摘要"）。

**验收**：模拟一个已关闭的 Conversation，调用 summarize，检查返回的 JSON 字段完整且合理。

### 步骤 4：接入 MemoryUpdater

**当前状态**：MemoryUpdater 的 4 条规则已实现，但：
- `update()` 从未被调用
- `apply_recurring_topics()` 需要外部提供 topic_counts，从未接入
- conversations.json 中已关闭的 conv 没有 summary/outcome/key_points

**接入方式**：在交互循环中，Conversation 关闭后立即触发：

```python
# Conversation 关闭钩子
closed_conv = conv_mgr._close_active(...)

# 1. 生成摘要（步骤 3）
summarizer.summarize(closed_conv, llm_chat)

# 2. 更新长期记忆
updater = MemoryUpdater()
updater.update(closed_conv)

# 3. recurring_topics（规则 1）
topic_counts = conv_mgr.count_topic_in_recent(topic, n=10)  # 已有方法
updater.apply_recurring_topics(topic_counts)

# 4. 写回文件
updater.save()
```

**注意**：`apply_decay()` 未接入（它是时间驱动而非事件驱动，需在启动时单独调用）。详见 5.5。

**问题**：`conv_mgr.count_topic_in_recent()` 统计的是已关闭 conv 的 topic。但规则 1 的描述是"同一 topic 在最近 10 个 Conversation 中出现 ≥3 次"。这里有一个歧义——是闭包的 10 个还是包括活跃的？当前实现只统计 closed，暂时够用。

**验收**：运行交互循环，触发一次 Conversation 关闭，检查 `relationship_state.json` 是否自动更新了 `recurring_topics` 或 `conflict_level`。

### 步骤 5：交互式循环（重写 run.py）

**定位**：将一次性 CLI 脚本改为持续运行的交互循环。

**核心结构**：

```python
def main():
    # ---- 阶段 0: 初始化 ----
    rs_path = ROOT / "relationship_state.json"
    if not rs_path.exists():
        bootstrap(rs_path)          # 步骤 2: 引导式初始化

    rs = load_relationship_state()
    conv_mgr = ConversationManager()  # 自动从 conversations.json 恢复
    updater = MemoryUpdater()

    print("魔鬼聊天已启动。输入消息开始，输入 /quit 退出。")
    print(f"[当前关系] stage={rs['stage']}, trust={rs['trust_level']}")

    # ---- 阶段 1: 交互循环 ----
    while True:
        her_msg = input("\n她: ").strip()

        if her_msg == "/quit":
            break
        if not her_msg:
            continue

        # --- 消息理解 (LLM) ---
        mu = MessageUnderstanding()
        llm_output = llm_chat(mu.system_prompt, mu.build_user_prompt(
            [{"role": "她", "content": her_msg}]
        ))
        ms = mu.parse_to_state(llm_output)

        # --- 需求识别 (规则) ---
        recognizer = NeedRecognizer(rs)
        need_result = recognizer.prioritize(ms)

        # --- 目标确定 (规则) ---
        planner = GoalPlanner(rs)
        goal_result = planner.plan(ms, need_result["top_needs"])

        # --- Conversation 引擎 ---
        timestamp = datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%S")
        prev_conv = conv_mgr.get_active_conversation()
        conv, switched = conv_mgr.process_message(her_msg, timestamp, goal_result["goal"])

        # --- Conversation 关闭钩子 ---
        if switched and prev_conv is not None:
            _on_conversation_closed(prev_conv, conv_mgr, updater, llm_chat)

        # --- 上下文构建 (规则) ---
        cb = ContextBuilder(rs, conv, [{"role": "她", "content": her_msg}])
        ctx = cb.format_for_llm()

        # --- 策略选择 (规则) ---
        selector = StrategySelector(relationship_state=rs)
        strategy_result = selector.select(ms, goal_result, need_result)

        if not strategy_result["primary"]:
            print("[警告] 无可用策略卡")
            continue

        # --- 回复生成 (LLM) ---
        generator = ReplyGenerator(relationship_state=rs)
        reply_result = generator.generate(
            llm_chat, ms, strategy_result["primary"],
            goal_result, chat_history=[{"role": "她", "content": her_msg}],
            conversation_context=ctx,
        )

        # --- 表达增强 (LLM) ---
        enhancer = ExpressionEnhancer(relationship_state=rs)
        enhanced = enhancer.enhance(llm_chat, reply_result["reply"], ms, strategy_result["primary"])

        print(f"\n回复: {enhanced['enhanced_reply']}")
        print(f"  [{reply_result['strategy_used']} | {goal_result['goal']}]")


def _on_conversation_closed(closed_conv, conv_mgr, updater, llm_chat):
    """Conversation 关闭钩子：生成摘要 → 更新记忆 → 写回文件"""
    # 1. 生成摘要
    summary_result = summarize_conversation(closed_conv, llm_chat)
    closed_conv.summary = summary_result["summary"]
    closed_conv.outcome = summary_result["outcome"]
    closed_conv.key_points = summary_result["key_points"]

    # 2. MemoryUpdater
    updater.update(closed_conv)

    # 3. recurring_topics
    for topic in ["work", "exam", "family", "relationship", "dating", "conflict"]:
        count = conv_mgr.count_topic_in_recent(topic, n=10)
        if count >= 3:
            updater.apply_recurring_topics({topic: count})

    # 4. 写回
    updater.save()
    conv_mgr._save()

    print(f"\n[记忆] Conversation 已关闭: topic={closed_conv.topic}, outcome={closed_conv.outcome}")
```

**注意**：为保持简洁，循环内不打印完整 debug 信息。可以加一个 `/debug` 命令切换调试模式，但 MVP 不实现。

**命令列表**：

| 命令 | 功能 |
|---|---|
| `/quit` | 退出程序 |
| `/status` | 显示当前关系状态 |
| `/history` | 显示最近的 Conversation 列表 |

**确认点**：交互循环中 Conversation 关闭逻辑是否正确触发？需要验证：
- 第一条消息：必然触发创建新 conv（因为 active=None），此时 prev_conv=None，不触发关闭钩子
- 后续消息：时间间隔 < 30min 且 topic 不变 → continue，不触发
- 时间间隔 > 8h 或跨天 → close_and_new，触发关闭钩子 ✅
- 话题切换 + 时间 > 30min → close_and_new，触发关闭钩子 ✅

**验收**：
- 启动 → 输入消息 → 得到回复 → 输入 `/quit` → 退出
- 检查 `conversations.json` 包含对话记录
- 如触发了 close，检查 `relationship_state.json` 有更新

## 三、数据流全貌

```
首次启动
  │
  ├─ relationship_state.json 不存在
  │     → bootstrap.py 引导对话
  │     → LLM 提取画像
  │     → 写入 relationship_state.json
  │
  └─ relationship_state.json 存在
        → load_relationship_state() 加载
        → 进入交互循环

交互循环（每条消息）
  │
  ├─ 消息理解 → 需求识别 → 目标确定
  │
  ├─ ConversationManager.process_message()
  │     │
  │     ├─ 继续当前对话 → 输出回复
  │     │
  │     └─ 触发关闭 → _on_conversation_closed()
  │           ├─ summarizer: LLM 生成 summary + outcome + key_points
  │           └─ MemoryUpdater: 规则更新长期记忆
  │                 → relationship_state.json
  │
  │  启动时（待接入）
  │     └─ MemoryUpdater.apply_decay()  ← 定期清理过期 recurring_topics
  │
  └─ 上下文构建 → 策略选择 → 回复生成 → 表达增强
       → 输出回复
```

## 五、待解决问题

### 5.1 多轮对话的消息历史管理

交互循环中，`chat_history` 目前只传当前这一条消息：

```python
chat_history=[{"role": "她", "content": her_msg}]
```

这意味着回复生成器看不到本轮对话中之前的消息。实际场景中，同一 Conversation 内的前几轮消息应该传递给回复生成器。

**方案**：在循环中维护 `recent_messages: list[dict]`，每次追加，每次传给 ContextBuilder 和 ReplyGenerator。上限 20 条（超过自动裁剪）。Conversation 切换时清空。

**风险**：多轮消息增加 LLM prompt token 消耗。ContextBuilder 的 Layer 3 已限制最近 6 条，够了。

### 5.2 Conversation 的 summary 生成时机

当前设计：Conversation 关闭时立即生成 summary（同步 LLM 调用）。

问题：用户可能正在等待下一条回复，summary 生成会阻塞交互循环约 2-3 秒。

**简化方案（MVP 采用）**：同步生成。2-3 秒的阻塞在终端聊天场景中可接受。后续可改为异步。

### 5.3 引导式初始化中的 attachment_style

attachment_style（依恋风格）是心理学概念，用户可能不理解，LLM 从自然语言也很难可靠推断。

**处理**：LLM 不确定时填 null，不强制填充。消息理解 prompt 中依恋风格为 null 时，跳过依恋风格的消歧提示。

### 5.4 重复启动时的 bootstrap 触发

用户可能误删 `relationship_state.json`，或想重置关系。每次文件不存在都触发 B 路线初始化。

**简化方案**：不额外处理。文件不存在就初始化。如果用户想重置，手动删文件即可。

### 5.5 apply_decay() 衰减机制未接入

`memory_updater.py` 的 `apply_decay()` 已实现（30 天降权、60 天移除 recurring_topics），但从未在交互循环中被调用。

**问题**：`apply_decay()` 是时间驱动（定期检查），而非事件驱动（Conversation 关闭）。交互循环中没有"空闲时执行定期维护"的机制。不接入意味着 `recurring_topics` 只增不减，长期使用后可能残留已过期的条目。

**影响评估**：低优先级。短期（数周内）无感知影响，`recurring_topics` 在上下文中的权重有限。但长期运行后（数月），过期的 recurring_topics 会污染 Layer 1 上下文。

**建议方案**：每次启动时调用一次 `apply_decay()`，基于 `conversations.json` 中最近一次出现各 topic 的时间与当前日期的差值计算 ages dict。改动量约 10 行。
