# 魔鬼聊天 v2 — LangGraph + PostgreSQL 架构设计

Version: 2.0 | 2026-07-26

---

## 一、目标

将当前"手写流水线 + JSON 文件"架构升级为业界标准技术栈，保持业务深度不变，提升工程成熟度。

**核心目标：**
- LangGraph 替代手写 pipeline 编排 → 可观测、可中断、可恢复
- PostgreSQL + pgvector 替代 JSON 文件 → 持久化、可查询、可扩展
- 类型化记忆 + 证据溯源 → 记忆可回溯、可验证
- 多模型路由 → 降本 40%+

**非目标：**
- 不推翻业务逻辑（12 维需求识别、策略卡系统、边界裁决保留）
- 不做成 Agent（保持工作流本质，不引入自主决策循环）

## 三、数据模型 (PostgreSQL + pgvector)

> **⚠️ 本节风险总览：**
> - pgvector IVF 索引冷启动：数据量 < 1000 行时退化为顺序扫描，初期检索性能反而不如 JSON 文件
> - VECTOR(1536) 维度绑定 BGE-M3，切换 embedding 模型需要 ALTER TABLE + 重建索引
> - CHECK 枚举硬编码：新增 memory_type 需要数据库迁移
> - checkpoints 表无上限：每次图执行生成一个检查点，长期运行会膨胀到 GB 级，需要定时清理策略
> - 1536 维向量存储成本：每条消息 ~6KB，10 万条消息 ≈ 600MB 仅向量数据

### 3.1 表结构

```sql
-- 联系人
CREATE TABLE contacts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    wxid VARCHAR(255) UNIQUE NOT NULL,
    display_name VARCHAR(255)
);

-- 关系状态（替代 relationship_state.json 中的标量字段）
CREATE TABLE relationship_state (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    contact_id UUID REFERENCES contacts(id) UNIQUE,
    stage VARCHAR(50) NOT NULL DEFAULT 'acquaintance',
    trust_level INT DEFAULT 50 CHECK (trust_level BETWEEN 0 AND 100),
    intimacy_level INT DEFAULT 30 CHECK (intimacy_level BETWEEN 0 AND 100),
    conflict_level INT DEFAULT 0 CHECK (conflict_level BETWEEN 0 AND 5),
    warmth VARCHAR(20) DEFAULT 'neutral',
    personality_traits JSONB DEFAULT '[]',
    preferences JSONB DEFAULT '{}',
    future_events JSONB DEFAULT '[]',
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now()
);

-- 类型化记忆（替代 relationship_state 中的列表字段）
-- 启发：Affinity Agent 的 typed memory + ConvoLens 的 evidence tracing
CREATE TABLE memories (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    contact_id UUID REFERENCES contacts(id),
    memory_type VARCHAR(50) NOT NULL CHECK (memory_type IN (
        'user_fact',        -- 她的个人信息
        'shared_event',     -- 共同经历
        'commitment',       -- 她或我的承诺
        'boundary',         -- 她设立的边界
        'conflict',         -- 冲突事件
        'emotional_moment', -- 关键情绪时刻
        'milestone',        -- 关系里程碑
        'preference',       -- 她的偏好
        'recurring_topic',  -- 反复出现的话题
        'unresolved_issue'  -- 未解决的问题
    )),
    content TEXT NOT NULL,
    evidence_messages JSONB DEFAULT '[]',  -- [{msg_id, excerpt, ts}] 引自 ConvoLens
    confidence FLOAT DEFAULT 0.5 CHECK (confidence BETWEEN 0 AND 1),
    embedding VECTOR(1536),               -- pgvector，用于语义去重和检索
    importance INT DEFAULT 1 CHECK (importance BETWEEN 1 AND 5),
    source VARCHAR(50) DEFAULT 'auto',    -- 'auto' | 'manual' | 'bootstrap'
    created_at TIMESTAMPTZ DEFAULT now(),
    last_recalled_at TIMESTAMPTZ DEFAULT now(),
    recall_count INT DEFAULT 0,
    expires_at TIMESTAMPTZ                 -- 可选过期时间（如 60 天未确认自动降权）
);

-- 对话
CREATE TABLE conversations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    contact_id UUID REFERENCES contacts(id),
    topic VARCHAR(50) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'active',
    goal VARCHAR(100),
    start_time TIMESTAMPTZ NOT NULL,
    end_time TIMESTAMPTZ,
    summary TEXT,
    outcome VARCHAR(50),
    key_points JSONB DEFAULT '[]',
    emotion_trajectory JSONB DEFAULT '[]'   -- [{ts, emotion, intensity}] P3 预留
);

-- 消息
CREATE TABLE messages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id UUID REFERENCES conversations(id),
    contact_id UUID REFERENCES contacts(id),
    role VARCHAR(10) NOT NULL CHECK (role IN ('我', '她')),
    content TEXT NOT NULL,
    embedding VECTOR(1536),
    emotion VARCHAR(50),
    intent VARCHAR(50),
    need_scores JSONB,
    timestamp TIMESTAMPTZ NOT NULL
);
CREATE INDEX idx_messages_conv ON messages(conversation_id, timestamp);
CREATE INDEX idx_messages_embedding ON messages USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- 策略效果统计
CREATE TABLE strategy_metrics (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    contact_id UUID REFERENCES contacts(id),
    strategy_name VARCHAR(255) NOT NULL,
    total_uses INT DEFAULT 0,
    successes INT DEFAULT 0,
    partials INT DEFAULT 0,
    failures INT DEFAULT 0,
    success_rate FLOAT DEFAULT 0,
    best_emotions JSONB DEFAULT '[]',
    worst_emotions JSONB DEFAULT '[]',
    last_used TIMESTAMPTZ
);
CREATE UNIQUE INDEX idx_strategy_metrics ON strategy_metrics(contact_id, strategy_name);

-- LangGraph Checkpointer 使用的检查点表（自动管理）
CREATE TABLE checkpoints (
    thread_id VARCHAR(255) NOT NULL,
    checkpoint_id VARCHAR(255) NOT NULL,
    parent_checkpoint_id VARCHAR(255),
    checkpoint JSONB NOT NULL,
    metadata JSONB,
    created_at TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (thread_id, checkpoint_id)
);
```

### 3.2 与旧存储的映射

```
旧 (JSON)                          新 (PostgreSQL)
──────────────────────────────────────────────────────────
relationship_state.scalars     →   relationship_state 表
relationship_state.近期关键事件   →   memories (type=shared_event/emotional_moment)
relationship_state.recurring   →   memories (type=recurring_topic)
relationship_state.unresolved  →   memories (type=unresolved_issue)
relationship_state.strategy_*  →   strategy_metrics 表
conversations.json             →   conversations + messages 表
messages_log (嵌套在 conv)      →   messages 表
```

## 四、记忆系统重构

> **⚠️ 本节风险总览：**
> - **LLM 结构化提取质量**：在一次调用中同时生成 summary + typed memories，LLM 可能顾此失彼，摘要质量或记忆分类准确率下降。建议先用独立调用验证质量，确认后可合并
> - **去重阈值 0.15 未经验证**：Threa 在英文对话 PR 评论中验证的阈值，中文对话的 embedding 语义空间分布不同，可能需要 0.12-0.20 范围的调参
> - **证据 excerpt 可能被 LLM 改写**：如果 LLM 在 evidence 中改写原文而非引用原句，excerpt 无法在 messages 表中精确匹配，证据链断裂
> - **10 种记忆类型边界模糊**：`emotional_moment` vs `milestone`、`preference` vs `user_fact` 容易混淆，LLM 分类一致性存疑
> - **冷启动空检索**：新用户没有历史记忆，dedup 和 retrieval 都返回空，前 5-10 次对话的上下文质量低于当前 JSON 方案（当前至少有 bootstrap 数据）

### 4.1 类型化存储（替代 flat summary）

当前：Conversation 关闭 → 一段文本 summary + 扁平列表 key_points。

改为：

```
Conversation 关闭
  → LLM 摘要（保留）
  → LLM 提取结构化记忆片段
     [
       {type: "emotional_moment", content: "考研前夕频繁焦虑", evidence: [...], confidence: 0.8},
       {type: "shared_event",     content: "一起在图书馆复习",     evidence: [...], confidence: 0.9},
       {type: "recurring_topic",  content: "考研压力",           evidence: [...], confidence: 0.85},
     ]
  → 每条记忆检查语义去重（embedding cosine < 0.15 视为重复，引自 Threa）
  → 写入 memories 表
```

### 4.2 证据溯源（引自 ConvoLens）

每条记忆携带 `evidence_messages`：

```json
[
  {"msg_id": "msg_abc", "excerpt": "我好焦虑啊，感觉好多都没看", "ts": "2026-07-11T08:38:00"},
  {"msg_id": "msg_def", "excerpt": "我觉得自己考不上了",          "ts": "2026-07-11T19:35:00"}
]
```

用户/面试官可以回溯：这条记忆是基于哪条消息得出的，判断是否靠谱。

### 4.3 语义去重（引自 Threa）

写入前用 pgvector 余弦相似度检查是否与已有记忆重复：

```python
def is_duplicate(new_embedding, contact_id, threshold=0.15):
    result = db.query(
        """SELECT 1 FROM memories
           WHERE contact_id = %s
           AND embedding <=> %s < %s
           LIMIT 1""",
        contact_id, new_embedding, threshold
    )
    return result is not None
```

### 4.4 衰减机制（保留并增强）

| 记忆类型 | 衰减规则 |
|---------|---------|
| recurring_topic | 60 天未提及 → confidence × 0.5；90 天 → 删除 |
| unresolved_issue | 在后续对话中被标记为 resolved → confidence 降至 0 |
| emotional_moment | 不衰减（历史快照，值在于记录而非时效） |
| user_fact | 被新的相反事实覆盖 → 旧条目 confidence 降至 0.1 |

## 五、混合检索层（引自 ConvoLens）

> **⚠️ 本节风险总览：**
> - **0.6/0.4 权重未经中文验证**：ConvoLens 在英文 WhatsApp 数据集上验证，中文 + 微信场景的语义/关键词分布不同，RRF (Reciprocal Rank Fusion) 可能比加权求和更稳定
> - **PostgreSQL 中文全文搜索需额外扩展**：内置的 `tsvector` 不支持中文分词，需要安装 zhparser 或 jieba 扩展，或退回到 `ILIKE '%关键词%'`（性能差）
> - **pgvector IVF 索引需定期维护**：数据增长后索引精度下降，需要 `REINDEX` 或重建索引，否则召回率衰减
> - **语义搜索对短消息效果差**：微信消息多为短句（"嗯嗯""好的""哈哈"），embedding 区分度低，语义检索噪声大

### 5.1 对话内检索

场景：构建 LLM 上下文时需要检索"她上次提到考试是哪天"。

```
查询: "考试压力"
  ├── 语义搜索: pgvector cosine → top 20
  ├── 关键词搜索: PostgreSQL full-text search → top 20
  └── 融合 (0.6 × semantic + 0.4 × keyword) → top 10
```

权重 0.6/0.4 直接采用 ConvoLens 的验证成果。

### 5.2 记忆检索

场景：策略选择时需要"她最近 30 天的情绪记忆"。

```python
def recall_memories(contact_id, memory_type=None, days=30, limit=10):
    return db.query(
        """SELECT * FROM memories
           WHERE contact_id = %s
           AND (memory_type = %s OR %s IS NULL)
           AND created_at > now() - interval '%s days'
           ORDER BY importance DESC, recall_count DESC, created_at DESC
           LIMIT %s""",
        contact_id, memory_type, memory_type, days, limit
    )
```

## 六、LLM 路由（引自 Affinity Agent）

> **⚠️ 本节风险总览：**
> - **轻量模型可用性不确定**：DeepSeek R1-Lite 可能在未来被下线或改名，需要抽象路由层以便切换（如换用 DeepSeek-V2-Lite 或 Qwen-2.5-7B）
> - **BGE-M3 本地部署门槛**：需要 2-4GB GPU 显存做实时 embedding，CPU 推理约 200ms/条（15 条消息需要 3 秒），可能抵消检索带来的收益
> - **轻量模型质量退化**：表达增强切到轻量模型后，口语化质量可能下降，用户能感知到"回复没以前自然"。建议上线前做 50 条 A/B 对比
> - **API 成本估算粗略**：DeepSeek API 按 token 计费，分层 prompt（Section 7）增加 system prompt 长度，实际节省可能低于 40%

### 6.1 模型分配

```
任务                      当前模型        建议模型           节省
────────────────────────────────────────────────────────────
Message Understanding     DeepSeek-V3     DeepSeek-V3        0%
Summary + Memory Extract  DeepSeek-V3     DeepSeek-V3        0%
Reply Generation          DeepSeek-V3     DeepSeek-V3        0%
Expression Enhancement    DeepSeek-V3     轻量模型 (R1-Lite)   ~40%
Embedding 生成            无              BGE-M3 (本地)       新增
Memory 去重检查            无              BGE-M3 (本地)       新增
紧急度评分                规则            规则                0%
```

关键洞察：表达增强是"润色已有回复"，不需要 V3 级别的模型。用轻量模型可节省 ~40% 的单轮成本。

### 6.2 路由实现

```python
class ModelRouter:
    def __init__(self):
        self.heavy = ChatDeepSeek(model="deepseek-chat")     # V3
        self.light = ChatDeepSeek(model="deepseek-r1-lite")  # 轻量
        self.embedder = BGEM3Embedding(model="BAAI/bge-m3") # 本地

    def route(self, task: str) -> BaseChatModel:
        return {
            "understanding":  self.heavy,
            "summary":        self.heavy,
            "reply_gen":      self.heavy,
            "enhancement":    self.light,       # ← 降本关键
            "embedding":      self.embedder,
        }[task]
```

## 七、Prompt 架构改进

> **⚠️ 本节风险总览：**
> - **流程式 prompt 迁移风险**：Threa 的验证场景是英文 DM 对话边界检测，直接套用到中文情感对话的边界检测 + 策略选择，效果未知。建议先拿 20 个历史边界案例做对比测试
> - **分层模板 = 更长的 prompt**：5 个 block 拼接后 system prompt 可能从 800 tokens 膨胀到 2000+ tokens，每次 LLM 调用的输入成本 × 2.5，抵消一部分多模型路由的节省
> - **时间感知的刻板印象风险**：注入"深夜适合温暖收尾"可能让 LLM 每次深夜都回复"早点休息吧"的变体，显得机械。需要多样化指令
> - **block 之间可能冲突**：`time_block` 说"避免深入讨论"，但 `strategy_block` 说"深挖情绪需求"，LLM 收到的信号矛盾

### 7.1 分层模板（引自 AI-GF-python）

当前：每个 LLM 调用点独立写完整 system prompt，关系状态在每个 prompt 里重复。

改为：

```python
class PromptAssembler:
    """模块化 prompt 组装。"""

    def assemble(self, template: str, layers: dict) -> str:
        return template.format(
            persona_block      = self._persona(),
            relationship_block = self._relationship(),
            time_block         = self._time_context(),    # ← 新增
            strategy_block     = self._strategy(layers.get("card")),
            evidence_block     = self._evidence(layers.get("memories")),
        )
```

各个 block 独立维护，不同 LLM 调用按需选取：
- MessageUnderstanding: persona + relationship + time + recent_messages
- ReplyGeneration: persona + relationship + strategy + evidence + context
- Summary: conversation + relationship + memory_types

### 7.2 流程式 Prompt（引自 Threa）

当前：散文式描述系统角色和行为。

在需要精确决策的场景改用流程式：

```
旧（散文式 — 边界检测）:
"你需要判断是否应该开始一个新的话题..."

新（流程式 — 边界检测）:
1. 检查上一条消息距今是否超过 8 小时 → 是: 关闭旧对话
2. 检查话题是否切换 + 间隔超过 30 分钟 → 是: 关闭旧对话
3. 检查是否有明确的结束信号（"晚安""拜拜""去忙了"）
   → 第一条信号: 标记 pending_close
   → 下一条消息确认: 关闭旧对话
4. 通过以上检查 → 继续当前对话
```

同样改造 StrategySelector 的推理部分（当前纯规则不用改，但如果有 LLM 辅助决策就改用流程式）。

### 7.3 时间感知（引自 AI-GF-python）

在 prompt 中注入时间上下文，影响回复基调和话题建议：

```python
def _time_context(self) -> str:
    hour = datetime.now().hour
    if 23 <= hour or hour < 5:
        return "当前是深夜。对方可能希望轻松或温暖的收尾。避免深入讨论沉重话题。"
    elif 5 <= hour < 9:
        return "当前是早晨。适合简短问候和一天的轻松开场。"
    elif 9 <= hour < 18:
        return "当前是白天。适合正常对话节奏。"
    else:
        return "当前是晚间。对方可能结束一天后比较疲惫，适合关心和倾诉。"
```

## 八、主动通知引擎（引自 AI-GF-python）

> **⚠️ 本节风险总览：**
> - **"活跃时间段"检测需足够数据**：少于 30 天的消息历史无法可靠推断她的活跃模式，冷启动期通知可能在不合适的时间推送
> - **告警疲劳**：4 个触发条件如果同时满足，用户一次收到 4 条通知 = 直接忽略。需要合并 + 优先级排序
> - **后台任务可靠性**：FastAPI background task 在服务器重启后丢失，APScheduler 需要持久化作业状态（用 DB 或 Redis），否则任务不可靠
> - **WCF 依赖**：通知触发需要实时消息流，WCF SDK 未接入前整个通知系统只能靠 mock 测试

### 8.1 触发条件

当前：用户被动打开仪表盘查看。

改为：后台定期检查，满足条件时推送：

| 条件 | 建议 |
|------|------|
| unresolved_issue ≥ 3 条 + 距上次对话 > 24h | "有 3 个未解决的问题，建议主动联系" |
| 她的活跃时间段 + conflict_level 上升 | "冲突可能升级，建议在今晚她活跃时段联系" |
| 策略成功率连续 3 次 < 0.5 | "当前策略效果不佳，建议调整策略偏好" |
| 距上次互动 > 48h | "已 2 天未互动，建议发起轻松话题" |

### 8.2 实现

LangGraph 的 `astream_events` + 定时任务（FastAPI background task 或 APScheduler）：

```python
async def check_proactive_conditions(contact_id):
    state = await load_state(contact_id)
    triggers = []
    if len(state.unresolved) >= 3:
        triggers.append(Alert(type="unresolved_batch", ...))
    if state.conflict_level > 2:
        triggers.append(Alert(type="conflict_risk", ...))
    return triggers
```

## 九、LangGraph StateGraph 设计

> **⚠️ 本节风险总览：**
> - **LangGraph 版本不稳定**：当前 pre-1.0，API 可能在下一个小版本中 break。建议锁定版本 + 写集成测试覆盖关键路径
> - **TypedDict 无运行时校验**：`PipelineState` 中某个 node 写错字段名（如 `emotion_intensity` 写成 `intensity`），LangGraph 不会报错，下游 node 读到 None 才炸，定位困难。建议用 Pydantic BaseModel 替代 TypedDict
> - **PostgresSaver 检查点膨胀**：每个 thread 的每次节点执行生成一个完整的 State JSONB 快照。10 次对话 × 9 nodes = 90 个检查点，每个数 KB → 快速增长。需要定时清理旧检查点
> - **`astream_events()` API 不稳定**：这是 LangGraph 中最频繁变动的 API，不同版本的 event 格式不同，SSE 桥接代码可能需要反复适配
> - **条件边调试困难**：如果 routing lambda 有 bug（如 `state["conversation_switched"]` 被错误地设成了字符串而非 bool），执行会无声地走错分支，不会报错
> - **异步嵌套陷阱**：FastAPI 的 async endpoint → `graph.astream()` → 内部 node 的 async DB 调用，三层 async 嵌套下异常堆栈几乎不可读

### 9.3 关键代码骨架

```python
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver

# 图定义
builder = StateGraph(PipelineState)

# 添加节点
builder.add_node("message_understanding", message_understanding_node)
builder.add_node("need_recognition", need_recognition_node)
builder.add_node("goal_planning", goal_planning_node)
builder.add_node("conversation_engine", conversation_engine_node)
builder.add_node("summarize_and_extract", summarize_and_extract_node)
builder.add_node("dedup_and_persist", dedup_and_persist_node)
builder.add_node("retrieve_context", retrieve_context_node)
builder.add_node("strategy_select", strategy_select_node)
builder.add_node("reply_generate", reply_generate_node)
builder.add_node("enhance_reply", enhance_reply_node)
builder.add_node("persist_result", persist_result_node)

# 边
builder.set_entry_point("message_understanding")
builder.add_edge("message_understanding", "need_recognition")
builder.add_edge("need_recognition", "goal_planning")
builder.add_edge("goal_planning", "conversation_engine")

# 条件分支：对话关闭？
builder.add_conditional_edges(
    "conversation_engine",
    lambda state: "summarize_and_extract" if state["conversation_switched"] else "retrieve_context",
    {
        "summarize_and_extract": "summarize_and_extract",
        "retrieve_context": "retrieve_context",
    }
)
builder.add_edge("summarize_and_extract", "dedup_and_persist")
builder.add_edge("dedup_and_persist", "retrieve_context")

# 条件分支：observe 模式跳过后面的 LLM 调用？
builder.add_conditional_edges(
    "retrieve_context",
    lambda state: "strategy_select" if state["mode"] == "intervene" else END,
    {"strategy_select": "strategy_select", END: END}
)
builder.add_edge("strategy_select", "reply_generate")
builder.add_edge("reply_generate", "enhance_reply")
builder.add_edge("enhance_reply", "persist_result")
builder.add_edge("persist_result", END)

# 编译（带 PostgreSQL Checkpointer）
checkpointer = PostgresSaver.from_conn_string(DB_URL)
graph = builder.compile(checkpointer=checkpointer)
```

## 十一、迁移路径

> **⚠️ 本节风险总览：**
> - **时间估算偏乐观**：1-1.5 周是"一切顺利"的估算，LangGraph 学习曲线（StateGraph 概念、Checkpointer、streaming）单独就需要 2-3 天。实际建议按 3 周排期
> - **JSON → PostgreSQL 数据迁移陷阱**：中文编码在 Windows/PostgreSQL 之间可能出现乱码；`近期关键事件` 是自由文本列表，迁移到 typed memories 需要 LLM 辅助分类（否则全是 `shared_event`）
> - **迁移期间系统不可用**：两个存储系统不能共存（数据不一致），需要在迁移窗口内完成，建议先在 staging 分支做迁移验证
> - **回滚方案缺失**：如果 LangGraph 版本有 bug 或 PostgreSQL 性能不如预期，需要有"一键切回旧流水线"的能力。建议保留 `process_message()` 作为 fallback，通过配置开关切换
> - **asyncpg vs psycopg**：LangGraph 的 PostgresSaver 内部使用 psycopg（同步），FastAPI 用 asyncpg（异步），两者共用同一个连接池可能冲突。需要验证连接池兼容性
> - **pgvector 环境可用性**：云数据库（RDS、Supabase）支持 pgvector，但本地开发需要手动安装。如果面试时想在笔记本上演示，需要 Docker Compose 一键启动

### 阶段 1：基础设施（1-2 天）
1. 安装 PostgreSQL + pgvector 扩展
2. 写 Alembic 迁移脚本，创建所有表
3. 写 `backend/db.py` — asyncpg 连接池
4. 写数据迁移脚本：JSON → PostgreSQL

### 阶段 2：LangGraph 集成（2-3 天）
1. 定义 `PipelineState`
2. 将当前 9 步 pipeline 封装为 9 个 Node
3. 构建 StateGraph，配置条件边
4. 接入 PostgresSaver（checkpointer）
5. 把 FastAPI router 改为调用 `graph.astream()`

### 阶段 3：记忆系统升级（1-2 天）
1. 实现类型化记忆提取（在一次 LLM 调用中同时生成 summary + structured memories）
2. 实现 `memory/dedup.py`（embedding 门控）
3. 实现 `memory/retrieval.py`（混合检索）
4. 修改 ContextBuilder 使用检索到的记忆替代 `近期关键事件`

### 阶段 4：多模型路由 + Prompt 重构（1 天）
1. Expression Enhancement 切到轻量模型
2. 分层 prompt 组装器
3. 边界检测 prompt 改为流程式

### 阶段 5：高级功能（按需）
1. 主动通知引擎
2. Emotion Trajectory（前文 P3 项）
3. 多联系人支持

**总预估：1-1.5 周（可业余时间分批完成）**
