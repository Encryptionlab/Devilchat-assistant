# 消息理解批量化改造设计

Version: 1.0 | 2026-07-26 | 作者: Saber (PM)

---

## 一、背景

### 1.1 问题

MessageUnderstanding 模块的设计假设是"单条消息 → 单次分析"。但微信真实场景中，对方经常连发多条消息（burst），且中间可能掺杂我的回复：

**场景 A：她的连续 burst**
```
她: "今天好累啊"
她: "复习了一整天"      }  同一个情绪单元的连续输出
她: "头都晕了"
```

**场景 B：中间掺杂我的回复**
```
她: "今天好累啊"
我: "怎么了宝宝"          ← 我的回复会影响她下一句的情绪走向
她: "复习了一整天"
她: "头都晕了"
```

当前 `pipeline_service.py` 的处理方式：

```python
her_msgs = [m for m in messages if m.get("role") == "她"]  # 滤掉我的消息
combined = " ".join(m["content"] for m in her_msgs[-3:])   # 硬拼接
```

两个问题：三条消息揉成一段文本，丢了边界和递进；更重要的是滤掉了我自己的消息，LLM 看不到"她是在回复我的关心"这个关键上下文。

### 1.2 数据源问题：固定条数 vs Conversation 边界

当前从 buffer 中"取最后 N 条"的做法有隐患——如果 buffer 里刚好跨越了一次话题切换：

```
消息缓冲（最近 5 条）
├─ [13:00] 她: "老板又发火了"        ← 属于 Conversation A (work)
├─ [13:01] 她: "项目要延期了"        ← 属于 Conversation A
├─ [14:30] 她: "复习不完了"          ← 属于 Conversation B (exam)
├─ [14:31] 她: "明天考试"            ← 属于 Conversation B
└─ [14:32] 她: "好紧张"              ← 属于 Conversation B
```

按"最后 5 条"硬截，work 和 exam 两个话题被混在一起送给 LLM，分析结果自然混乱。

正确的做法：**由 ConversationManager 的 messages_log 提供数据源**。ConversationManager 已经做好了边界检测（话题切换 / 超时 / 跨天），它的 messages_log 天然只包含当前活跃对话的消息。数据源从"buffer 取最后 N 条"改为"取活跃 Conversation 的 messages_log，上限 15 条"。

### 1.3 约束

- **成本**：burst 中 N 条消息必须仍为 1 次 LLM 调用，不能逐条分析
- **兼容性**：下游模块（NeedRecognizer → GoalPlanner → StrategySelector → ReplyGenerator）不改动
- **混合消息**：输入包含她+我的完整交换，LLM 需能区分角色并聚焦分析她的消息
- **数据源**：使用 ConversationManager.messages_log（天然按话题分好），而非 MessageBuffer 的原始缓冲

## 二、改造方案

### 2.1 核心思路

**输入从"拼接文本"升级为"消息序列"，输出保持单个 MessageState 结构，新增少量字段描述递进关系。**

成本不变（1 次 LLM 调用），信息密度提升。

### 2.2 输入格式变更

**当前（只取她的消息，硬拼接）：**
```
## 对话历史
她: 今天好累啊复习了一整天头都晕了    ← 三条消息被硬拼成一句；我的回复被丢弃
```

**改为（完整时间线，角色标签，逐条列出）：**
```
## 消息序列（时间顺序，共 5 条）

1. 她: 今天好累啊
2. 我: 怎么了宝宝
3. 她: 复习了一整天
4. 她: 头都晕了
5. 我: 这么拼啊

请分析她在以上序列中的消息（标记为"她"的条目），考虑整个交换的上下文，仅输出 JSON。
```

设计要点：
- **包含双方消息**：我的回复是她后续消息的"因"，LLM 需要看到才能准确判断她情绪的变化方向（是得到安慰后缓和了，还是我说错话后升级了）
- **明确角色标签**：每条消息带 `她:` / `我:` 前缀，LLM 能区分哪条待分析、哪条是上下文
- **数据源为 messages_log**：由 ConversationManager 提供，天然按话题边界切分好，不会跨 Conversation 混入无关消息
- **上限 15 条**而非 5 条：messages_log 最多保留 100 条，取最近 15 条保证上下文足够且 token 可控

### 2.3 输出结构变更

MessageState 现有 14 个字段**全部保留不动**。新增 3 个字段：

```python
burst_pattern: str       # burst 结构模式
emotional_peak: str      # burst 内最强情绪
trajectory_note: str     # 情绪/需求递进概括
```

#### burst_pattern 枚举

| 值 | 含义 | 示例 |
|----|------|------|
| `single` | 单条消息，无 burst | "在干嘛" |
| `venting` | 倾诉递进，情绪逐步加强 | "好累" → "复习了一天" → "头都晕了" |
| `escalating` | 情绪升级，可能转向冲突 | "你怎么又不回" → "算了每次都这样" |
| `question_chain` | 连续提问，可能有焦虑 | "你在哪" → "跟谁" → "什么时候回来" |
| `mixed` | 混合型，话题/情绪跳跃 | "今天好累。你中午吃的啥" |

#### emotional_peak

burst 中情绪最强烈的那条消息对应的情绪标签。通常取自最后一条（递进终点），但不总是。

#### trajectory_note

一句话概括整个 burst 的情绪/需求递进轨迹，例如：
- "从疲惫倾诉到寻求安慰"
- "从不满到失望"
- "从分享到邀约"

### 2.4 保留字段的语义调整

原有字段在批量模式下仍保持其含义，但分析范围从"单条"变为"整个序列"：

| 字段 | 原有语义（单条） | 新语义（序列） |
|------|-----------------|---------------|
| `emotion` | 这条消息的情绪 | 整个序列的主导情绪 |
| `emotion_intensity` | 这条消息的强度 | 整个序列的峰值强度 |
| `need_scores` | 这条消息的需求打分 | 覆盖整个递进过程的综合需求 |
| `surface_intent_scores` | 这条消息的意图打分 | 序列的复合意图 |
| `topic` | 这条消息的话题 | 整个序列的话题（不变） |

下游模块读取的字段名不变，因此 **NeedRecognizer / GoalPlanner / StrategySelector 不需要任何改动**。

### 2.5 System Prompt 改动

关键改动是任务描述和分析原则部分。

**当前任务描述：**
> 你的任务：接收她的最新消息和对话上下文，输出结构化的消息分析结果。

**改为：**
> 你的任务：接收她的一段消息序列（可能 1~5 条连发），分析整体的情绪基调、情绪递进轨迹、核心需求，输出结构化的分析结果。
>
> 分析原则：
> 1. 如果多条消息构成"倾诉递进"（如：累 → 复习了一天 → 头晕），主导情绪取递进终点的最强情绪，需求要覆盖整个递进过程
> 2. 如果多条消息是"话题跳跃"（如：累 → 问你今天干嘛了），按最后一条确定主导方向和话题
> 3. 如果只有一条消息，正常分析即可
> 4. burst_pattern 判断标准：看消息之间的因果关系，而非时间顺序
>    - venting：后一条加深前一条的情绪（累 → 越来越累 → 扛不住了）
>    - escalating：情绪从负面到更负面，有冲突升级趋势
>    - question_chain：连续提问，每条都在寻求信息
>    - mixed：话题之间无明显递进关系，各说各的

新增输出字段说明追加到 prompt 末尾的 JSON 模板中。

## 三、改动范围

### 3.1 需要改的文件

| 文件 | 改动内容 | 改动量 |
|------|---------|--------|
| `src/message_understanding.py` | MessageState 加 3 字段；`_build_system_prompt()` 重写任务描述（序列分析 + 混合角色）+ 加 burst 字段定义；`_REQUIRED_FIELDS` 新增字段加入；burst_pattern 枚举校验 | ~50 行 |
| `backend/services/pipeline_service.py` | `observe_messages()` 数据源从 `her_msgs[-3:]` 拼接改为取 `conv_mgr.get_active_conversation().messages_log` 最近 15 条，完整时间线输入 | ~10 行 |
| `backend/services/pipeline_service.py` | `analyze_pending()` 同上调整 | ~5 行 |

### 3.2 不需要改的

- `need_recognition.py` — 读 `ms.emotion` / `ms.need_scores`，字段名不变
- `goal_planner.py` — 读 `ms.emotion` / `need_result`
- `strategy_selector.py` — 读 `ms` 和 `need_result`
- `reply_generator.py` — 读 `ms.emotion` / `ms.dominant_intent`
- 前端 — 只展示 `emotion` / `topic` / `dominantNeed`，不感知 burst 字段

## 四、成本分析

| 方案 | LLM 调用/ burst | 优势 | 劣势 |
|------|----------------|------|------|
| 逐条分析 | N 次 | 每条精细 | 成本 × N，分析割裂 |
| 拼接成一段（当前） | 1 次 | 便宜 | 丢消息边界，递进丢失 |
| **序列化输入（本方案）** | **1 次** | 便宜 + 保留递进 | prompt 略长（+~200 tokens） |

以 burst=3 条为例，序列化输入比拼接多 ~100-200 tokens（序号 + 换行），占一次 LLM 调用总 token 的 5-8%，可忽略。

## 五、风险与边界

1. **messages_log 为空时兜底**：如果活跃 Conversation 的 messages_log 为空（极端情况：ConversationManager 刚初始化、还没记录任何消息），回退到 MessageBuffer 的 `get_conversation_context(15)` 作为输入源
2. **混合消息中"她"的消息太少**：如果 15 条里有 13 条是"我"的、只有 2 条是"她"的，LLM 分析焦点可能分散。可在 prompt 中加一句"请重点分析标记为'她'的消息，'我'的消息仅作上下文参考"
3. **Conversation 关闭时的处理**：当边界检测触发 `close_and_new` 时，先取旧 Conversation 的 messages_log 完成摘要，再对新 Conversation 重新开始记录。流水线中 `observe_messages()` 已按顺序处理（先摘旧、再记录新），不冲突
4. **单条消息仍可正常处理**：`burst_pattern = "single"`，下游对 `emotion` / `need_scores` 的读取不受影响
5. **LLM 输出新增字段可能缺失**：`parse_response()` 中新增字段设默认值（`single` / `neutral` / `""`），不回退到旧版本也不会崩
6. **burst_pattern 判断依赖 LLM 质量**：不用于任何自动化决策，仅作为分析展示和未来可能的策略微调参考
7. **15 条上限与 token 预算**：15 条中文消息约 600-1000 tokens（含角色标签），在总预算 ~2000 tokens 内安全

## 六、与现有架构的关系

```
ConversationManager.messages_log（完整时间线，她+我，按话题边界切分）
  │  最近 15 条
  ▼
MessageUnderstanding（本改造）
  输入: 完整消息序列（角色标签 + 逐条列出）
  输出: MessageState（原有 14 字段 + 新增 3 字段）
  │
  ├─  emotion / need_scores（字段不变，下游不动）
  ▼
NeedRecognizer → GoalPlanner → StrategySelector → ReplyGenerator
  │
  └─  burst_pattern / trajectory_note（新增，未来可用）
     策略微调 / 仪表盘展示（远期）
```
