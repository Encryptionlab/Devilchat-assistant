## 四、LLM 调用分布

```
干预轨道 (process_message)         观测轨道 (observe_messages)
─────────────────────────────      ──────────────────────────────
LLM #1  消息理解                     LLM #1  批量序列分析
LLM #2  摘要生成 (仅切换时)           LLM #2  摘要生成 (仅关闭时)
LLM #3  回复生成 (流式)               
LLM #4  表达增强 (流式)

典型延迟: ~8-15s                   典型延迟: ~10-40s (批量 15 条)
流式感知: ~5s                        无流式 (后台静默)
```

## 六、关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 编排方式 | 固定流水线 | 可控、可调试、成本可预测 |
| LLM 角色 | 算子而非 Agent | 每个 LLM 调用的输入/输出明确，不互相决策 |
| 策略选择 | 规则为主 + 效果加权 | LLM 做策略选择不可靠，规则可解释 |
| 状态存储 | JSON 文件 | 单用户 MVP，避免数据库依赖 |
| 并发模型 | asyncio + 线程池桥接 | LLM 调用是同步的，桥接到 async 生态 |
| 流式方案 | SSE + Queue | 用户边等边看，感知延迟从 12s 降到 5s |
| 效果学习 | Evaluator + 统计加权 | 不微调模型，只调整策略选择权重 |
